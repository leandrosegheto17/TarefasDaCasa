1. TDD: `test/integracao/rotas/entrar-codigo.test.ts`.
2. Rota: lê ou cria o `tdc_aparelho` pelo módulo do TP-0025 e obtém o IP.
3. Caso de uso `entrarComCodigo({codigo}, {aparelhoId, ip})`:
   1. Consulta o bloqueio de aparelho e de IP **antes** de validar ou consumir. Se bloqueado, responde 429 `bloqueado` com `segundosRestantes` (`entrar-codigo-bloqueado.json`).
   2. Faz o hash do código normalizado e chama `consumir`, que devolve o membro e o tipo, ou nada.
   3. Sem retorno (código inexistente, expirado, usado ou invalidado), ou membro removido: registra a falha nas duas chaves e responde 400 `codigo_invalido` com a mensagem do aceite (`entrar-codigo-erro.json`).
   4. Corpo com formato inválido também conta falha e recebe a **mesma** resposta 400, para não revelar o formato.
   5. Sucesso: zera a chave do aparelho e chama `criarSessaoAparelho`, que não revoga as outras sessões do membro (CA-07.5). Responde 200 `{membro, precisaCriarAcesso: true}` quando o membro é Responsável sem credencial (L-01, sessão provisória derivada). Nos outros casos, sem esse campo.

## 2. Plano de teste
Integração. As fábricas criam família, Criança e Responsável sem credencial, e os códigos são gravados por `banco/codigos.gravarInvalidandoAnteriores` com hash. O relógio fixo vale para o limite. O cookie `tdc_aparelho` é fixado por teste.

| Caso | Esperado |
|---|---|
| Código de Criança, com e sem hífen e em minúsculas | 200, `Set-Cookie` `tdc_sessao` e sessão sem `precisaCriarAcesso` (via `GET /api/situacao`) |
| Código de Responsável | 200 com `precisaCriarAcesso: true`. A situação confirma a sessão provisória |
| Mesmo código usado de novo | 400 `codigo_invalido` |
| Código expirado (`expira_em` no passado do relógio) | 400 |
| Código invalidado por outro mais novo | 400 |
| Formato inválido | 400 |
| 5 falhas no mesmo aparelho | a 6ª, mesmo com código válido, recebe 429 com `segundosRestantes` 600, e o código continua não usado. Outro `tdc_aparelho` ainda entra |
| 30 falhas do mesmo IP com aparelhos variados | 429 |
| Dois aparelhos com dois códigos do mesmo membro | duas sessões ativas (CA-07.5) |
| Sem `tdc_aparelho` | o cookie é criado na resposta |
| Sem `Origin` | 403 |

Comando: `pnpm --filter @tdc/api test:integracao -- entrar-codigo`.

## 3. Plano de validação de segurança
- G-21 / RN-18: bloqueio conferido antes do consumo; uso único atômico pelo `UPDATE ... RETURNING` do TP-0026; 5 falhas por aparelho → 10 min; 30 por IP → 1 h.
- G-17: só o hash do código é usado na consulta; o código em claro não vai para log nem para `registro_erro`.
- Ameaças:
  - Troca de `tdc_aparelho` para fugir do limite: coberta pela chave de IP. Testar.
  - IP falsificado por cabeçalho: só o cabeçalho que a plataforma confia. Conferir no diff.
- A sessão provisória não dá acesso a outras rotas (G-15 e TP-0023). Testar com `GET /api/hoje` → 401 ou 403, conforme o TP-0023.
