# TP-0096 — Backup diário criptografado e restauração ensaiada (sessão `[U]` no GitHub)

Reserva: Livre
ID no TASK.md: TP-0096 · Lote: Lote 20 · Agente: executor · Chapéu: Backend + [U] · Est: 2,5 h · Dep: TP-0004 · Status no TASK.md: Pendente
Reqs: ADR-007; RNF-13; SDD §6 Troca de dados (restauração) · Aceite: `.github/workflows/backup.yml` diário e manual: `pg_dump` com o papel só leitura, criptografado com `age` (chave pública em secret), artefato por 30 dias; com o usuário: secrets `BACKUP_DATABASE_URL` e `AGE_PUBLIC_KEY` criados e a chave privada guardada por ele; restauração ensaiada num branch do Neon em menos de 30 min, com o procedimento no `.md/DEPLOY.md`

## 1. Plano de execução
**Reaproveitamento:** USAR o papel `tdc_leitura` e o projeto Neon (`sa-east-1`, PG 17) criados no spike TP-0004; o padrão de workflow do `ci.yml` (TP-0002: `permissions: contents: read`, actions oficiais por versão maior). Nada de código do app.
**Camada:** `.github/workflows/backup.yml` (SDD árvore alvo); seção "Backup e restauração" no `.md/DEPLOY.md` (criar se não existir; TP-0095 e TP-0097 escrevem em paralelo, reler antes de editar).
**Referência visual:** não se aplica

Feito pelo agente:
1. `backup.yml` com `on: schedule: cron '0 6 * * *'` (03:00 de Brasília, UTC-3), `workflow_dispatch` e `workflow_call` (o `deploy.yml` do TP-0097 chama este mesmo workflow; não criar segundo job de dump). `permissions: contents: read`; `concurrency: backup`.
2. Passos: `pg_dump` 17 pela imagem `postgres:17` (`docker run --rm`), porque o cliente do `ubuntu-latest` pode ser de outra versão e o dump de servidor 17 exige cliente ≥ 17; `-Fc --no-owner --no-acl` em `BACKUP_DATABASE_URL` com `sslmode=require` e host **sem** `-pooler` (pg_dump pelo pooler em modo transação não é confiável). Falha se o código ≠ 0, se o arquivo tiver 0 bytes ou se `pg_restore --list` falhar (ADR-007 item 6). Criptografar com `age -r "$AGE_PUBLIC_KEY"` (pacote `age` do apt), apagar o dump em claro no mesmo passo, `actions/upload-artifact` com `retention-days: 30` e `if-no-files-found: error`. Nome `backup-<AAAAMMDD-HHMM UTC>.dump.age`.
3. `DEPLOY.md`: baixar (`gh run download <id> -n <artefato>`), `age -d -i <chave> -o backup.dump`, criar branch do Neon `restauracao-<data>` sem dados ou banco novo nele, `pg_restore --no-owner --no-acl -d <url dono do branch>`, conferir contagens, trocar `DATABASE_URL` na Vercel (Production) e redeploy; volta atrás = variável anterior (SDD §6). Ensaio a cada 6 meses (ADR-007 item 5).
4. Registrar no `.md/DEPLOY.md` o prazo do próximo ensaio.

Feito pelo usuário (sessão guiada):
- Na própria máquina: `age-keygen -o tdc-backup.key`; guardar a chave privada no gerenciador de senhas e numa cópia offline. A chave privada nunca é mostrada ao agente nem colada no chat.
- GitHub > Settings > Secrets and variables > Actions: `AGE_PUBLIC_KEY` (linha `age1...`) e `BACKUP_DATABASE_URL` (URL do `tdc_leitura`, host direto).
- Neon (SQL Editor): conferir `GRANT SELECT` em todas as tabelas e `ALTER DEFAULT PRIVILEGES FOR ROLE tdc_dono ... GRANT SELECT ON TABLES TO tdc_leitura` (e `USAGE` nas sequências), senão o dump falha nas tabelas das migrações futuras.
- Disparar o workflow manualmente; ensaio cronometrado: download, `age -d`, branch, `pg_restore`, contagem, apagar o branch.
PENDENTE: (1) ADR-007 item 2 fala em chave pública "versionada no repositório" e o aceite pede secret `AGE_PUBLIC_KEY`. Proposta: seguir o aceite (secret). (2) Esta tarefa está na R1 e o schema de produção só nasce no primeiro `deploy.yml` (TP-0097, R2): antes disso o dump é de banco vazio e o ensaio não prova nada. Proposta: entregar workflow, secrets e procedimento aqui; o ensaio cronometrado roda logo depois do primeiro deploy (schema + `migracao_aplicada` preenchida), ainda antes do TP-0099, comparando tabelas e linhas de `migracao_aplicada`. Confirmar com o Coordenador.

## 2. Plano de teste
- Estático: `actionlint .github/workflows/backup.yml` limpo (o mesmo passo de `actionlint` do TP-0097).
- Falha fechada: um run manual com `BACKUP_DATABASE_URL` de senha errada num fork/branch de teste sai vermelho (ou prova local do mesmo script de shell com URL inválida → código ≠ 0 e nenhum artefato).
- Run real: `workflow_dispatch` verde, artefato `.age` > 0 bytes, retenção 30 dias visível na página do run.
- Ensaio: tabela em `## 4` com o tempo de cada etapa (total < 30 min), contagem por tabela produção × restaurado e o branch apagado no fim.
- Evidência: link do run, nome e tamanho do artefato, tabela do ensaio. Sem URL, senha nem conteúdo do dump.

## 3. Plano de validação de segurança
- ADR-007 e TASK §1.3: dump só com `tdc_leitura` (conferir no Neon que `INSERT` com ele falha); a chave privada nunca entra no repositório, nos secrets nem no log; `gitleaks` verde.
- No diff: segredos só via `${{ secrets.* }}` em `env:` do passo (nunca interpolados no `run:`), nenhum `echo` do secret, nenhum `set -x`; o dump em claro só existe no runner e é apagado antes do upload; o artefato enviado é só o `.age`.
- `permissions: contents: read`; sem `pull_request` como gatilho (secrets não ficam expostos a PR); actions oficiais por versão maior.
- G-14: o agendamento é operação fora da aplicação; o workflow não chama API do app nem gera ocorrência.
- TLS: `sslmode=require` na conexão do dump.
